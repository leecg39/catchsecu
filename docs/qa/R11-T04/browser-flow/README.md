# 응답 정정·메모 CRUD·동의 PDF·입력 보호

2026-10-10. 실제 게시 폼에 익명으로 제출한 응답을 관리자 UI에서 처리했다. 로컬 시험 데이터만 사용했다.

- 메모 생성 → 수정 → 삭제를 UI로 수행했다. DB에는 메모가 남지 않고 각 변경의 감사 이벤트가 한 건씩 저장됐다.
- 이름을 정정하고 사유와 전후 답변을 화면·독립 DB에서 확인했다. 사유와 답변 원문은 암호화되어 있고 감사 원장에는 원문이 없다.
- 동의 영수증을 UI에서 PDF로 내려받았다. 실제 PDF 41,580바이트의 SHA-256이 DB의 PDF 해시와 일치했다. PDF 파서로 1페이지·120일 내용·JavaScript 없음도 확인했다.
- `unsaved-before.json`: 정정 사유를 입력한 상세 창이 확인 없이 닫히는 문제를 재현했다. `SubmissionDetail.tsx`에 닫기·취소 확인과 미저장 탐색 보호를 추가했다.
- `conflict.json`: 다른 요청이 먼저 저장한 다음 UI의 오래된 수정이 충돌했다. 입력을 보존하고 저장을 막았다. 최신 응답 재조회는 입력 버리기 확인 후 수행했다.
- `conflict-recovered.json`: 최신 상태를 바탕으로 다시 수정해 저장하고 새로고침에서 확인했다. 메모 입력도 닫기 취소 시 보존되고 명시적 버리기 후에만 사라졌다.
- `db-after-conflict.json`: 최종 응답 version4, 정정3건, 메모0건. UI에서 받은 감사 CSV의 사건 ID·폼 이름·응답 ID가 독립 DB의 3건과 일치했다. 최초 검증 `db.json`은 정정1건 시점이며 덮어쓰지 않았다.

서버는 새 production 프로세스 PID73349에서 확인했다. 타입·변경 파일 린트·production 빌드가 통과했다. 전체 첨부·공유·철회·파기·정보주체 수용은 아직 남아 있다.

재현 명령: Node24 환경에서 `node --env-file=.env.local --import tsx scripts/qa-rea-correction-db.ts --after-conflict`. 현재 전용 fixture가 이 시점 상태일 때 사용한다. 후속 업무로 fixture가 바뀌면 이전 상태를 덮어써 검증하지 않는다.
