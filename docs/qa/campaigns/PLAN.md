# 캠페인·수신자·예약 발송 구현 계획

P08-T02를 중심으로 P08-T04·P09-T01/T02의 공통 부분을 연결한다. 전역 72 Task는 유지하며 아래 항목은 실행 순서다. 선행 발신자 검증은 [기록](../senders/README.md)에 있다.

## 확인한 범위

- 기존 서비스 진입점: src/components/services/index.tsx. 직접 입력/폼 대상 이메일은 유료 안내, SMS는 발신번호 안내로 이동한다. MessageHistory는 빈 표다.
- 원본 mail/direct·mail/catchform은 유료 제한 상태를 관찰했다. mail/history·sms/history는 발송 요청/예약 탭과 열·필터를 확인했다. 실제 유료 작성 흐름·거래 결과는 관찰하지 못했으므로 아래 작성·상태 계약은 독립 구현이다.
- 대상 화면: /mail/direct, /mail/catchform, /mail/history, /sms/direct, /sms/catchform, /sms/history. 기존 발신자 관리 두 화면으로 연결한다.
- 현재 발송 기반: jobs.ts의 임대·재시도, marketing.ts의 수신 근거/동의 잠금, sender-access.ts의 발신자 검사, private file/ClamAV와 파기 처리. 이 기반을 재사용한다.

## 데이터와 권한

1. **Campaign**: 회사·서비스·생성 구성원·채널·출처, 제목·암호화 내용, 발신자 ID와 예약 시 버전, 상태·예약 시각·version. 초안만 내용/대상 편집, 초안 삭제 가능, 요청 이후에는 취소·보관 및 최소 이력 보존.
2. **CampaignRecipient/Delivery**: 캠페인·정규화 연락처 HMAC 유일 키, 암호화 연락처, 당시 MarketingPreference/Submission/동의 버전, 예약·처리·제외·성공/실패 상태, Job·공급자 결과 연결. 타 회사·서비스 연결을 DB 복합 FK로 거부한다.
3. **CampaignEvent**: 버전·행위·수행자·시각의 불변 이벤트. 본문·연락처·비밀·인증값은 감사 로그에 넣지 않는다.
4. message.read/manage/send를 사용한다. 대상 선택은 현재 marketing.read와 서비스 grant를 다시 확인한다. 개인정보 전체 조회 권한이 없는 발송 담당자에게 원본 응답 전체를 노출하지 않는다.
5. 마케팅 발송은 직접 입력/CSV 입력만으로 동의를 생성하지 않는다. 등록된 같은 서비스·채널의 동의와 원본 보유 기한을 확인한다. 동의 없는 연락처·중복·잘못된 형식은 미리보기에서 제외 이유를 보여준다.
6. 최초 단계는 현재 검증된 마케팅 발송 계약을 사용한다. 일반 업무 알림의 별도 처리 근거·템플릿은 추가 계약과 검증 없이 마케팅 동의 검사를 우회하지 않는다.

## API와 화면 연결

- /campaigns GET/POST, /campaigns/:id GET/PATCH/DELETE.
- /campaigns/:id/recipients: 목록·추가·삭제 또는 초안의 원자적 대상 교체. page/pageSize와 명시적 선택 ID를 사용하고 화면에 보이는 일부 행을 전체로 취급하지 않는다.
- /campaigns/:id/preview, schedule, reschedule, cancel, archive, retry. 변경마다 현재 version, 즉시/예약 요청은 Idempotency-Key.
- /campaigns/:id/deliveries와 export, /campaign-sources. 조회는 회사·서비스·역할과 삭제/기한 상태를 적용한다.
- 이메일 작성은 텍스트에서 시작하되 HTML sanitizer, 첨부, 변수 템플릿은 P09-T01의 별도 검증을 마쳐 연결한다. 지원하지 않는 내용 형식을 조용히 버리지 않는다.

## 반드시 해결할 연결점

- **작업 유형**: 새 캠페인 정책을 모르는 이전 worker가 전송할 수 없도록 새 유형을 사용한다. Sender Job DB 제약에도 새 유형을 명시하고 이전 유형으로 변경을 막는다. migration 전 기존 worker 전부 중지, 이후 같은 버전으로 재시작한다.
- **잠금 순서**: 기존 회사/서비스→원본 응답→동의 연락처→발신자 흐름을 보존한다. 캠페인/작업 잠금은 그 뒤에 두며 네트워크 호출·예약 취소와의 교착을 시험한다. 실제 전달 여부가 정해지기 전에 성공 상태를 기록하지 않는다.
- **전달 결과**: 로컬 메일 파일 생성, SMTP 접수, 공급자 최종 수신은 별도 상태다. SMTP 접수만으로 최종 전달 완료나 반송률 0을 표시하지 않는다.
- **원문 삭제**: eraseMarketingJobs, 응답 파기 증명서와 worker 정리에 새 캠페인/수신자 사본을 포함한다. 새로 복사한 개인정보를 기존 파기 밖에 남기지 않는다.
- **외부 의존성**: SMS/LMS/MMS 실제 전송·단가·잔액은 P08-T03/P10-T03, 외부 이메일 반송·complaint·수신거부는 P09-T02에서 연결한다. 미설정 시 실패/준비 필요 상태를 반환하고 가짜 성공을 만들지 않는다.

## 최종 증거

격리 PostgreSQL 통합 로그, 실제 로컬 메일 바이트와 From/수신자 대조, 예약 취소 후 파일 부재, 재시작 후 DB 상태, 권한 회수·철회·파기 경합 결과, Ego 캡처와 모바일 측정, 외부 공급자 검증 여부를 별도 기록한다. 전 페이지 완료는 각 원본 경로의 수용 조건까지 검증한 뒤에만 선언한다.

로컬 범위의 위 실행 묶음은 검증했다. C07의 외부 가격과 C10의 외부 공급자 실제 전달은 남아 있다. C11은 실제 두 worker와 임대/sending 저장 상태를 재현한 복구 시험이며 OS 강제 종료 시험은 하지 않았다. C12의 첨부는 다음 이메일 내용 계획에 포함한다. 전체 Task 완료 체크는 올리지 않는다.
