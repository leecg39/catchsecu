## 실제 PostgreSQL 경합 6개

별도 `catchsecu_test`의 합성 회사·작성자/소유자, 아홉 질문·행렬 행·선택 수·분기·게시 문서·필수 첨부를 사용했다. API handler와 PostgreSQL, 실제 ClamAV를 사용하며 결과를 모의 처리하지 않았다.

1. 같은 version 초안 저장 두 건은 200/409로 한 번 반영되고 버전·질문/분기와 쓰기 감사가 일치했다.
2. 승인 요청/저장은 한 요청만 반영됐다. 승인 snapshot/hash와 실제 게시/아홉 응답이 연결됐다.
3. 승인 결정/수정이 모두 성공한 순서에서도 이전 승인은 `superseded`이고 새 내용은 409 `APPROVAL_REQUIRED`로 거부됐다. 재요청/재승인 이후 게시했다.
4. 승인/반려 두 결정은 200/409로 결정·감사를 한 번만 남겼다.
5. 새 게시/수정은 한 요청만 반영되고 고정 주소·기존 공개 종료/유지와 현재 초안이 일치했다. 최초 응답 암호문·게시 버전·파일·영수증 행/실제 PDF 바이트는 유지됐다.
6. 기존 응답 파기 worker와 새 게시본의 파일/응답 제출·영수증 열람을 함께 실행했다. 파기 뒤 기존 답변 9개·영수증 1개·첨부와 캐시 원문/해시를 제거하고 PDF/첨부를 410으로 차단했다. 새 응답의 답변 9개·영수증 1개·파일·불변 폼 버전은 유지하고 증명서 해시·파기 수량을 대조했다. 파기 worker는 시험 DB에서만 실행했다.

처음 다섯 시험은 잠금 관측 장치가 트랜잭션의 통계 스냅샷을 갱신하지 않아 대기를 0으로 기록했다. 제품 결과를 경합 통과로 집계하지 않았다. 관측 시 `pg_stat_clear_snapshot()`을 사용해 실제 대기 2개를 확인하고 해제했다. [PostgreSQL 17 통계 관측 문서](https://www.postgresql.org/docs/17/monitoring-stats.html)를 참고했다. 새 6개와 관련 전체 **4파일·39개**가 통과했다. 최종 전체 회귀는 **46파일·614개·실패/대기 0**, 361.26초다. 관련 시험에서는 승인/수정이 200/200, 전체 회귀에서는 409/200으로 끝나는 두 순서를 관측했고 두 경우 모두 현재 내용에 유효한 승인만 사용했다. 타입과 변경 파일 린트는 오류·경고 0이다.

## Production API 67개·실제 PDF

[준비 51개](http-prepare.json)와 [서버 재시작 후 16개](http-finish.json)가 통과했다. localhost `catchsecu_dev`의 이름·소속·계정을 검증한 합성 회사에서 보관 원본을 독립 복사했다. 기존 사용자 관리자 계정과 브라우저 제어를 변경하지 않았다.

최초 독립 폼 게시→아홉 유형/필수 ClamAV 파일/문서 동의 제출→영수증 PDF 다운로드·한국어/문서 해시/실행 스크립트 없음 파싱→원본 문서 수정/새 게시→같은 폼의 새 문서 연결→두 초안 저장 경합→게시/수정 경합→고정 주소 재연결→최초 영수증 보존→새 응답/새 영수증→보관→현재 PDF/파일 권한과 공개 종료를 확인했다. 두 production 경합 모두 대기 2개가 기록됐고 수정 요청이 승리했다. 새 version을 읽어 게시했으며 기존 PDF는 같은 바이트였다.

최종 DB는 대상 폼 1개·게시 버전/링크 2개·응답/영수증/파일 각 2개와 고정 주소를 연결한다. 최초 영수증의 암호화 증거·PDF·본문 해시와 최초 응답/게시 버전/파일 해시는 문서·폼 재게시, 보관, PID 70784→97506 서버 재시작 후 같았다. 새 영수증에는 새 문서의 증거 문구가 포함되고 최초 영수증에는 포함되지 않는다. 조회자는 403, 미인증은 401이며 소유자의 보관 자료 다운로드는 유지했다.

첫 API 준비에서는 문서 수정의 필수 전체 DTO를 빠뜨려 422로 종료됐다. 계약에 맞춰 수정했으며 이전 실패 합성 폼은 API로 보관했다. 실패 로그와 당시 PDF를 따로 보존하고 성공 사례로 집계하지 않았다. 원본 동의서 수정은 이 합성 회사의 검증용 문서에만 적용했다. 전역 production 파기 worker와 외부 전송은 실행하지 않았다.
