# 본문·페이지·완료·마감 화면 구현 계획

상태: BI-01~07을 완료했다. rich 동의 증거·이미지 PDF 영수증 v2에 이어 신규 격리 폼의 4개 표시 영역 전체 수명주기, 반응형·RTL·키보드·실패·production 재시작, 기존 frozen fixture 20/20 보존까지 통과했다. 문항 이미지 QI 체크포인트와 별개이며 R08 전체 완료를 뜻하지 않는다.

## 근거와 구현 경계

원본 번들 `main.183e9d2c.js`의 SHA-256은 `3538d47856c6ba1b4207059dc09434066c7ca692a5907ed792dd9e27c7dba78f`, 재사용 REA 증거는 `ev_87493e79c4f053718022b23e1e5d42acf1af245f8c7838a89cd7ebc3918df152`다. 원본 발췌·위치는 `source-review.json`, 기존 코드 영향은 `backend-impact.json`에 별도로 기록한다. 두 조사가 확정되면 아래 계약을 재대조한 뒤 첫 구현을 시작한다.

- 원본 `mainText`는 폼 설명 HTML, `pageContent`는 페이지 HTML이다. 첫 페이지 title/content는 저장 때 비워지고 폼 설명이 첫 안내를 담당한다.
- 완료 `endPageContent`와 마감 `privatePageContent`/`privatePageType`은 원본 managements 설정이다. PRIVATE는 공개 접수가 닫혔을 때의 화면이며 관리자 비밀 페이지가 아니다.
- 원본 본문 이미지는 JPEG/PNG, 14 MiB다. HTML 안의 URL, figure 폭·정렬, alt를 사용한다. 로컬은 암호화 자산과 인가된 읽기를 위해 owned asset ID를 저장한다. 원본 서버의 소유권·검사·역사 보존은 관측하지 못했다.
- 원본 페이지 복사의 본문 URL 치환·용량 계산에는 정적 추적만으로 확정할 수 없는 부분이 있다. 로컬은 본문도 새 소유 자산 ID로 복제하고 전체 용량을 계산한다.
- 원본 HTML 렌더가 안전하게 정제된다는 증거는 없다. 로컬은 실행 가능한 HTML을 저장·렌더하지 않는 명시적 계약을 사용한다.

## 결정과 데이터 계약

### 1. 표시 문서와 구형 평문

`RichDocumentV1`은 `schemaVersion: 1`과 허용된 구조만 갖는 JSON 문서로 구현한다. 원본 HTML은 편집기 입출력 경계에서 이 구조로 변환한다. URL을 포함한 원본 HTML을 그대로 DB에 넣지 않는다. 허용할 실제 toolbar와 HTML 출력 형태는 원본 조사 결과에 맞춰 계약을 고정한다.

첫 계약은 단락, h2/h3/h4 제목, 굵게/기울임, 링크, 줄바꿈, 목록/들여쓰기, 인용, 표, 이미지와 허용 제공사의 미디어를 표현한다. 원본 추가 도구인 글자 크기 12/14/15/16/20/24/32px·글자색·RTL, 이미지 caption, 표 colspan/rowspan도 계약에 포함한다. 이미지 노드는 문서 내 안정적인 노드 ID·자산 ID·대체 텍스트·정렬·폭을 갖는다. 일반 링크는 http/https만, 이미지 원격 URL·data/blob URL·스크립트·이벤트·임의 CSS·iframe 원문은 거절한다. 제공사 미디어는 정규화된 제공사/영상 식별자를 사용하고 원격 자원을 서버에서 가져오지 않는다. 구체적인 첫 wire·함수·상한은 [CONTRACT.md](CONTRACT.md)를 따른다.

기존 `body`는 평문이다. 새 `bodyRich`가 없으면 기존 직렬화와 표시를 유지한다. 새 편집기는 bodyRich의 텍스트 투영을 body에 함께 보낸다. 현재 bodyRich가 있는데 구클라이언트가 이를 생략하면 기존 body가 동일한 경우에만 rich 문서를 유지한다. body를 바꾸면서 rich 필드를 생략한 모호한 요청은 422로 거절한다. 명시적 null은 rich 제거이며 전송한 body를 평문으로 사용한다. 과거 버전에서 값을 찾아 복원하지 않는다. 페이지/완료/마감 필드도 생략 보존과 명시 제거를 구별한다.

구형 행에 새 문서를 백필하지 않는다. 새 nullable 필드가 null이면 DTO에 생략하여 기존 JSON·승인 지문·영수증 증거가 바뀌지 않게 한다. 제출·정정에는 작성자 문서를 받지 않고 고정된 FormVersion에서 읽는다.

### 2. 페이지와 이동 — F4 선행 작업

`FormPage`라는 기존 목록 응답 타입 이름은 재사용하지 않는다. 버전 소유 `FormSection`을 도입하여 DB 행 ID와 안정적 pageKey, 순서, 제목, rich 본문, 기본 목적지, 뒤로 이동 정책을 저장한다. 질문은 같은 FormVersion의 페이지를 가리키며 전체 질문 100개 제한을 유지한다. 기존 폼은 페이지 모델이 null인 단일 페이지로 읽는다.

원본의 순번/offset을 그대로 영구 식별자로 쓰지 않는다. 공개 계약의 목적지는 `{kind: page, pageId}` 또는 명시적인 동의/제출 종료점, 참여대상 제외 종료점이다. 원본 99999/PATH_KILL을 정상 제출로 해석하지 않는다. 보기별 이동은 안정적 question/option ID를 참조한다. 원본 조건 우선순위와 다중 선택 처리 규칙을 조사하여 F4 계약에 고정하기 전까지 분기를 구현 완료로 세지 않는다.

페이지 CRUD는 전체 초안의 낙관적 version 검사 안에서 원자적으로 처리한다. 추가·정렬·복제·질문 이동·제목/본문 수정·삭제를 제공한다. 삭제로 끊어지는 이동/질문 참조는 사용자가 확인한 명시적 변경과 함께 저장한다. 자기 이동·잘못된 대상·종료할 수 없는 순환·중복 페이지/질문 배치를 서버에서 거절한다. 로컬 페이지 50개 상한은 원본 추가 handler의 UI 제한과 맞추며 원본 서버 상한으로 표현하지 않는다. 원본 분기는 RADIO/SELECTBOX 및 한 페이지당 분기 질문 하나로 관측됐다. 로컬 선택형/드롭다운에 이를 매핑하고 체크박스에 임의 분기 우선순위를 만들지 않는다.

서버는 제출 답변으로 실제 방문 경로를 다시 계산한다. 미방문/숨김 질문의 답변과 첨부 주입을 거절하고 방문한 필수 질문을 검사한다. 뒤로 가기와 분기 변경 시 화면에서도 미방문 답변/임시 첨부를 명시적으로 정리한다. 재시도 키·정정·CSV·PDF·공유의 경로 의미를 함께 시험한다.

### 3. 완료·마감 설정과 공개 범위

완료 및 마감 안내는 승인·게시와 함께 고정되는 FormVersion 설정으로 구현한다. 원본 managements의 독립 저장 방식과 다른 로컬 설계임을 명시한다. 편집 화면에서 변경한 내용은 재게시 후 적용되며 기존 게시/응답에는 소급하지 않는다. 기본 안내와 직접 작성 모드를 분리한다.

| 요청 상태 | 허용 콘텐츠 | 쓰기/제출 |
| --- | --- | --- |
| 활성 접수 | 폼 본문, 페이지/질문, 동의 화면 | 기존 접수 규칙 적용 |
| 정상 제출 성공 | 해당 게시본 완료 안내 | 성공 재전송은 동일 응답 유지 |
| 일시중지·정상 기간 종료·응답 한도 | 해당 게시본 마감 안내만 | 기존 410/409 거절 유지 |
| 회수된 토큰·보관/삭제·회사/서비스 비활성 | 기존 비공개 오류 | 거절 |
| 관리자 폼/승인/과거 응답 | 권한을 통과한 정확한 버전 | 현재 역할/보유 기한 적용 |
| 선택 공유 viewer | 선택된 질문과 그 질문이 있는 페이지 안내; 폼 본문은 명시적 공유 계약에 포함할 때만 | 읽기 전용 |

기존 활성 폼 읽기 가드를 약화하지 않고 별도의 안내 화면 읽기 경계를 둔다. 완료 화면은 성공 결과에 묶인 짧은 읽기 증명으로 표시한다. 마감/완료 자산을 활성 공개 manifest에 섞지 않는다. 토큰 회수·기한 경과가 읽기 중 발생한 경우 마지막 검사에서도 차단한다. viewer의 신규 본문 공유 정책은 기본 비공개로 시작하고 공유 설정·DTO·DB·실제 읽기 범위가 일치하도록 명시적으로 구현한다.

### 4. 자산·참조·자원 상한

용도는 폼 본문/페이지/완료/마감을 구별한다. 같은 슬롯 안에서 이미지를 반복하면 노드별 참조를 보존하되 소유 자산 용량은 중복 계산하지 않는다. 질문 없는 참조는 slot + document/pageKey + nodeKey로 식별하며 기존 questionKey를 가짜 UUID로 채우지 않는다.

한 FormContent의 질문·본문·페이지·종료 안내 자산을 모아 한 번에 잠그고, 이전 pin 제거 → 모델 변경 → 새 pin 추가를 같은 트랜잭션에서 수행한다. 기존 질문 전용 primitive를 별도로 반복 호출하여 다른 슬롯 pin을 지우지 않는다. 직접 SQL에 대한 projection, parent/FK/용도/tenant/service/검사 상태, 영구 삭제·GC fencing도 같은 전체 그래프를 검사한다.

14 MiB는 새 본문 이미지 용도에만 적용한다. 기존 문항/보기 1 MiB·참고 자료 5 MiB·제출 첨부 10 MiB 제한을 유지한다. DB Blob/Asset, HTTP 본문 읽기, 저장 암호화/복호화, S3 길이, 실제 ClamAV 데몬의 11M 제한을 모두 점검한다. 확장된 내부 인프라 한도가 다른 업로드 기능의 공개 상한을 넓히지 않도록 호출자가 용도별 상한을 넘긴다.

이미지 디코딩은 원본 바이트 한도와 별도로 픽셀·프레임·폭/높이·동시 처리 상한을 둔다. 본문 이미지의 최초 로컬 한도는 24M pixels·단일 프레임·한 변 16,384px, 디코딩 동시 2개다. 기존 질문 이미지 8M pixels/8,192px 제한을 바꾸지 않는다. 부하 시험에서 실행 가능한 값을 확인하며 변경하면 근거를 기록한다. 문서별 20,000 UTF-16 텍스트, 256 KiB JSON, 2,000노드·깊이 12·이미지 32개, 폼 전체 rich JSON 512 KiB·이미지 노드 100개를 초기 안전 상한으로 시험한다. HTTP JSON 요청 전체 1,000,000 bytes 제한 안에서 질문·동의·기타 설정의 공간을 남기며 요청 전체 한도도 별도로 검사한다. 원본에서 관측한 제한으로 표현하지 않는다.

복제/템플릿 사용은 전체 자산을 새 소유 ID로 만들고 모든 문서의 노드 참조를 치환한다. 같은 서비스 템플릿 등록은 독립 pin을 만든다. 현재 초안 제거 후에도 게시본·승인·과거 응답 참조가 있으면 물리 삭제하지 않는다.

### 5. 영수증·PDF

기존 ConsentEvidence v1과 저장된 PDF는 그대로 읽는다. 신규 rich 폼은 v2 증거와 전용 렌더 경로를 사용한다. root 및 실제 방문 페이지의 rich 문서, 자산 SHA/용도/표시 메타데이터, 페이지 경로를 증거에 포함한다. 완료/마감 안내는 동의 전 제시한 본문이 아니므로 동의 증거에 섞지 않는다.

새 PDF는 고정 버전의 검증된 이미지 bytes를 읽어 넣는다. 원격 URL fetch와 현재 초안 참조는 금지한다. 전체 해독 pixels·최종 PDF bytes·페이지 수를 제한하고 게시 전 가장 큰 허용 동의 조합을 preflight한다. 원본 이미지 hash와 PDF용 변환 hash를 구분하고 제출 시 확정된 PDF bytes를 암호화 저장한다. 이후 다운로드에서 재생성하지 않는다. 기존 다국어/RTL 렌더와 정정 전 영수증 bytes 보존을 회귀 검증한다.

BI-07a/07b 결과는 [전체 수용 기록](full-acceptance/README.md)에 고정했다. 네 문서 슬롯의 실제 CRUD·게시·제출·개정 이력, 복제/템플릿 독립성, 3개 viewport·RTL·키보드, 장애 회귀 22개, production 82페이지 build, 재시작 해시와 기존 fixture 20/20이 통과했다.

## 구현 순서와 소유권

1. 두 read-only 조사 결과와 이 계획을 확정한다. 다음으로 BI-02a의 순수 계약 및 시험부터 작성한다. 선행 계약을 고정하기 전 DB/UI 코드를 동시에 변경하지 않는다.
2. 독립 작업이 생기면 기존 두 담당자에게 서로 다른 파일 범위를 배정한다. root는 계약·통합·DB/시험/Ego 실행과 최종 기록을 맡는다. 모든 DB·migration·실행 시험·브라우저 변경은 root가 직렬 수행한다.
3. 적용된 migration 1~124와 frozen QA 20세트는 수정하지 않는다. 신규 nullable 필드는 기존 데이터에서 null임을 확인한 뒤 읽기 전용 비교에만 제외한다. 새 테스트는 별도 fixture를 만들며 비밀·PDF·업로드 원본은 ignored `.local`에 보관한다.
4. product 변경 후 필요한 관련 회귀를 실행한다. 과거 전체 시험을 현재 통과로 합산하지 않는다. 전체 수용 전에는 Task의 제품 구현과 부분 검증만 기록한다. 공식 107개 상태는 완료0/진행53/계획54를 유지한다.

## 실제 수용 시나리오

- 본문에 가로 PNG, 2페이지에 세로 JPEG, 완료/마감에 서로 다른 이미지를 넣는다. 원본 크기·지정 폭·alt·정렬·caption을 저장/새로고침하고 3폭에서 overflow와 자연 비율을 확인한다. 원본 config의 resizeUnit은 px이고 50/75 command 실동작은 미관측이다. custom drag에서 관측된 10~100%와 구별하여 로컬의 px/percent 명시 입력을 시험한다.
- 페이지 추가/복제/정렬/질문 이동·분기를 만든다. 정상 두 경로 제출, 뒤로 답변 변경, 숨긴 필수/첨부 주입, 삭제 페이지 참조, 오래된 탭 저장을 시험한다.
- 활성/한도/기간 종료/일시중지/회수 상태마다 화면과 이미지 실제 bytes 접근 범위를 비교한다. 활성 manifest에 완료/마감 이미지가 섞이지 않는지 확인한다.
- 제출 후 root/page 이미지를 교체하고 완료/마감 설정을 바꾸어 재게시한다. 이전 제출/정정/승인 snapshot/영수증 PDF는 원래 내용을 유지해야 한다.
- 템플릿 등록/사용/수정/삭제와 폼·페이지 복제로 새 자산 ID·같은 blob hash·용량을 확인한다. 원본 삭제가 복제본을 깨뜨리지 않아야 한다.
- viewer에서 선택 질문, 페이지 안내, 본문 공유 설정과 이미지 manifest가 정확히 일치해야 한다. 회수/보유 기한 후 원문·bytes 모두 차단한다.
- 14 MiB 경계·초과, MIME/확장자/hash 위조, 이미지 폭탄/다중 프레임, 실제 검사 실패/연결 실패, quota 경쟁·저장 실패·GC 경쟁을 검증한다.
- 새 production 프로세스로 재시작하고 신규 업무/이미지/PDF hash와 기존20세트를 읽기 전용 검증한다. 완료된 새 fixture를 동결한 이후에는 UI/HTTP로 다시 열지 않는다.
