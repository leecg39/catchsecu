# F3 질문 입력 패턴 검증

## 결과

`infoPatternId` 1·2·3·4·7·8을 독립 데이터 모델과 API 계약에 추가했다. 질문 유형과 정보주체 역할의 허용 조합을 Zod와 PostgreSQL `CHECK`가 함께 제한한다. 호출자가 보낸 정규식은 strict 계약에서 거부하며 서버는 동적 `RegExp`를 실행하지 않는다.

원본 번들에서 확인된 분류는 일반, 추가질의, 주민등록번호, 이메일, 주소, 날짜다. 실제 원본 `patternRegex` 값과 원본 서버 강제 규칙은 번들에 없으므로 복원했다고 주장하지 않는다. 주민등록번호는 고정 길이 문자 순회로 `000000-0000000` 형식만 검사한다. 이메일·주소·날짜는 기존 전용 질문 계약이 검증한다.

## 구현 범위

- `Question.infoPatternId` nullable 열과 ID·질문 유형·역할 조합 DB 제약
- 폼 생성·조회·수정·제거, 복제, 템플릿 사용, 게시본 지문 보존
- 공개 제출과 과거 게시본 정정의 서버 검증
- 편집 화면의 일반/주민등록번호 선택과 공개 화면의 숫자 키보드·14자 상한·자동 하이픈
- 구형 질문은 `NULL`과 API 필드 생략 의미를 유지

## Ego Lite 수용

1. 편집 화면에서 단문 질문의 입력 형식을 주민등록번호로 변경하고 자동저장 완료를 확인했다.
2. 게시 후 공개 화면에서 placeholder `000000-0000000`, 숫자 키보드, 자동 하이픈을 확인했다.
3. 12자리 값은 제출되지 않았고 PostgreSQL Submission 수가 0인 상태를 확인했다.
4. 13자리 값은 `900101-1234567`로 제출됐고 암호화 답변을 서버에서 복호화해 일치시켰다.
5. production 서버 재시작 뒤 편집 화면의 주민등록번호 선택과 DB 상태 해시 `9e30c2e55f005eb4a25b1c6838ae4d080f1d39afcc841fc5a224455349da60fc`가 유지됐다.
