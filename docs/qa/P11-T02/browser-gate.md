# P11-T02 브라우저·API 게이트 (2026-10-04 보강)

기존 서버 검증(105+100 시험·HTTP 77개) 위에 **실제 브라우저 조작과 라이브 API**로 잔여 수용 조건을 검증했다.
계정 `owner@catchsecu.local.test`·회사 A(`10000000`), dev 앱 :3100. 산출물은 전부 정리했다.

## IP 접근 관리 (`/security/ip`)

| 검증 | 방법 | 결과 |
|---|---|---|
| 규칙 등록→DB 저장 | 화면에서 `10.99.0.0/16` 등록 | 목록 표시 + `IpRule` 행 일치 |
| 자가 차단 방지(켜기) | 현재 IP 127.0.0.1 미포함 상태로 켜기 | 알림 "현재 접속 IP를 허용하는 규칙을 먼저 등록해주세요" — 저장 거부 |
| 비밀번호 재확인 | 켜기 다이얼로그 | 현재 비밀번호 필수 |
| 제한 활성화 | `127.0.0.1/32` 규칙 후 켜기 | `IpAccessPolicy.enabled=true` |
| 자가 차단 방지(삭제/비활성) | 제한 ON 상태에서 현재 IP 규칙 삭제·비활성 | 409 `IP_LOCKOUT` — "현재 관리자의 접속 IP를 허용하는 규칙을 유지" |
| 무효 CIDR | `999.1.1.1` | 422 `INVALID_CIDR` |
| IPv6 | `::1/128` 등록 | 저장 성공 |
| **IPv4-mapped IPv6** | `::ffff:127.0.0.1/128` | **`127.0.0.1/32`로 정규화 저장** — 매핑 우회 불가 |
| 중복 | 동일 CIDR 재등록 | 409 `ALREADY_EXISTS` |
| 테넌트 격리 | 회사 B 규칙 ID로 조회 | 404 `NOT_FOUND` |
| 권한 | viewer로 등록·목록 | 403 `FORBIDDEN` |
| 잘못된 비밀번호 | 설정 변경에 틀린 비밀번호 | 401 `INVALID_PASSWORD` |
| X-Forwarded-For 위조 | `203.0.113.9` 헤더로 요청 | 소켓 IP 기준이라 정책 우회 불가(허용 IP로 정상 처리) |
| 제한 해제·정리 | PATCH settings enabled=false + 규칙 삭제 | version 2·규칙 0건 |
| 감사 | AuditEvent | `ip_rule.created`×3·`ip_access.updated`×2·`ip_rule.deleted`×3 |

## 회사 2FA (`/security/two-factor`·`/setting`·API)

| 검증 | 결과 |
|---|---|
| 구성원 현황 | 10명 미등록·예외 0 실데이터 렌더(검색·상태 필터) |
| 잠금 방지 안내 | "관리자 본인의 2단계 인증을 먼저 등록" 링크 표시 |
| 본인 미등록 상태로 강제 PATCH | 409 `MFA_SETUP_REQUIRED` — owner 본인 미등록 시 강제 불가 |

## 보안 현황 (`/security/compliance` + `GET /api/v1/security/status`)

7개 점검 항목이 API 계산값과 화면이 일치: 회사 2FA·구성원 등록·복구 수단·추가 관리자·IP 제한 = 확인 필요, 비밀번호 12자·세션 45분/7일 = 설정 확인.
**방금 끈 IP 제한이 즉시 "꺼져 있습니다"로 반영** — 화면이 현재 DB 상태를 계산한다.

## 남은 조건

- owner 예외 만료·복구코드 실사용·예외 만료 후 기존 세션 즉시 차단의 브라우저 단은 기존 서버 시험(100개)과 HTTP 39개로 커버 — 추가 브라우저 재현은 2FA 실등록이 필요해 부작용이 크므로 유지.
