# 회사·서비스 저장 경계 검증

2026-10-10. 로컬 전용 PostgreSQL `catchsecu_test`에서 실제 API 핸들러·트랜잭션·DB 잠금을 사용했다. R03 전체 수용 완료는 아니다.

## 재현과 수정

- 회사 PATCH가 Company 행 잠금을 기다리는 동안 역할을 회수하거나 MFA를 강제하면, 기존 코드는 요청 시작 시 권한으로 주소·개정·감사를 저장했다. `before.json`과 `lock-before.json`에 200 응답과 실제 개정 증가를 보존했다.
- 초기 `before.json`의 session 사례는 별도 pg 연결의 시간대를 UTC로 고정하지 않아 만료 시각이 잘못 만들어졌다. 이 사례는 기존 결함의 증거로 집계하지 않는다. 이후 UTC 연결에서 실제 만료를 검사했다.
- 회사 등록에서도 Session 잠금 대기 중 만료시키면 201로 등록됐고, 세션 삭제는 인증 오류 대신 404가 됐다. `registration-before.json`, `registration-lock-before.json`은 이 별도 재현이다.
- 회사·서비스 변경은 구성원/보안 정책 변경과 같은 Company → 현재 사용자·멤버·정책·세션 → 서비스 순서로 잠근다. 트랜잭션 안에서 권한·IP·MFA·비밀번호·회사 선택·만료를 다시 검사하고, 감사 저장 후에도 시간 만료를 검사한다. 실패하면 업무 변경과 감사가 함께 롤백된다.
- 회사 등록은 User → Session 쓰기 잠금 뒤 계정·세션을 검사하고 회사·기본 서비스·멤버·정책·구독·선택값·감사를 한 트랜잭션에 저장한다.
- 회사·서비스 조회도 최신 권한을 확인한다. 서비스 목록은 마지막 유효 페이지로 보정하며, 같은 회사의 권한 회수는 기존 403 계약을 유지한다.

## 최종 결과

`regression-final.json`: **7개 파일 135개 통과, 실패·미실행 0**.

- 새 `management-authority.test.ts` 51개: 변경/파일/폐쇄 10개 작업의 역할·세션·MFA 변경 30개, 감사 뒤 자연 만료 10개, 조회 경계 6개, 페이지 보정·중복 생성·동시 수정 3개, 등록 세션 경계 2개.
- 기존 회사·서비스·파일, 컨텍스트 선택, 구성원 권한, 접근 요청, 동의서 표시 설정 회귀 84개.
- 실제 잠금 대기 증거는 `lock-observations.json`의 PostgreSQL PID와 대기 SQL로 확인한다. 시간 경과 시험은 실제 감사 저장 뒤 Date만 전진시켜 실제 DB 롤백을 검사했다.

중간 실패도 보존했다. `after.json`의 20개 실패는 마지막 소유자 보호 제약과 시험 연결 시간대 설정 오류였으며, 두 조건을 보완한 `after-fixture-correction.json`은 62개 통과다. `management-final.json`은 동시 생성/수정을 더한 64개 통과다. `related-regression.json`의 68통과/1실패는 서비스 조회의 403→404 계약 회귀였고 최종 코드에서 403을 복원해 135개를 재검증했다.

이 결과는 원본 전 경로 화면 동등성, 접근 요청의 모든 브라우저 상태, 전체 역할·외부 제공사 수용을 대신하지 않는다. 전체 1,834개 통과 보고서는 회사 관리 변경 전 구조화 처리방침 체크포인트이며, 이 변경에는 위 135개 관련 회귀를 적용했다.
