# P07-T02 마케팅 동의·차단 목록 점검 계획

P07-T01 검증 이후 진행 중인 작업이다. 현재 권한·기한·쿼리·화면과 발송 사본 삭제 순서를 보완하고 실제 PostgreSQL 검증을 진행한다.

## 현재 확인한 코드

- `src/contracts/marketing.ts`: 채널별 동의, 정규화 연락처, 목록 필터, 최대 100건의 고유 ID/version 일괄 입력과 DTO.
- `src/server/marketing.ts`: 서비스별 목록·상세·원본 응답 선택·근거 등록·제외·철회·원문 삭제·통계·발송 잠금. 조회/일괄 처리에서 `lockFileContext`의 기한을 보존하지 않는 부분이 있다.
- `src/server/marketing-jobs.ts`: 관련 큐·로컬 발송 사본·캠페인 연락처 삭제와 만료 정리.
- `src/app/api/v1/marketing/[...segments]/route.ts`와 `src/components/forms/Marketing.tsx`: API와 화면 연결. 쿼리·페이지·현재 작업 권한을 세부 점검해야 한다.
- `tests/server/marketing.test.ts`: 기존 23개 실제 PostgreSQL 사례. 채널/회사/서비스 분리, 낙관적 버전, 일괄 철회, 원본 파기, 발송 직전 차단과 잠금 경합이 있다.

## 다음 구현·검증 순서

1. 목록·상세·근거 선택·생성·제외·철회·삭제·CSV·통계를 현재 회사/계정/서비스/세션/MFA/비밀번호 정책으로 검사한다. 실제 잠금 대기와 감사/캐시 저장 뒤 기한 종료가 원문 반환이나 부분 변경을 남기지 않는지 검증한다.
2. 지원 쿼리와 중복 키, 현재 목록의 검색 의미, 정렬·페이지 보정을 명확히 한다. 같은 연락처가 다른 서비스/채널의 동의에 영향을 주지 않는지 실제 데이터로 대조한다. DTO에 현재 작업별 권한을 담아 화면에 연결한다.
3. 일괄 철회/삭제의 100건 제한·중복 ID·부분 미존재·현재 버전·반복 요청·새 동의 뒤 오래된 요청을 점검한다. 전체 원자성, 중복 이벤트/감사 0과 큐 원문 정리를 검사한다.
4. 현재 발송 차단은 원본 응답, 채널별 제외, 정보주체 suppression, 이메일 반송/수신거부를 함께 대조한다. 발송 잠금과 철회/파기/연락처 정정의 순서, 처리 도중 보유 기한 종료를 실제 PostgreSQL과 합성 로컬 수신 환경에서 검증한다.
5. 연락처·증거·CSV·선택한 원본 답변은 읽기 완료 시점의 보유 기한에 맞춰 반환한다. 수식 문자 방어, 정리 후 캐시 재실행, 관련 큐/로컬 사본/캠페인 사본의 삭제를 점검한다.
6. 자기 합성 회사와 수신자만 사용한 HTTP CRUD·일괄 처리·정리·재시작 대조, 타입·린트·필요한 회귀 테스트와 입력/결과 해시를 새 폴더에 기록한다. 기존 회사·계정·업무 데이터와 이전 QA 기록을 보존한다.
7. Job.localCopyErasedAt과 정리 대기 기록을 추가한다. API 삭제는 SQL 확정 뒤 파일을 지우며 실제 실패를 재시도한다. 파기 증명서는 연결된 마케팅 발송 사본 정리가 확인되기 전 발급되지 않는다. 이전 적용 SQL은 수정하지 않는다.
8. 합성 회사의 특정 Job만 실행하는 처리 범위를 제공한다. 동일 작업자 이름의 이전 시도는 증가한 attempts와 유효 임대로 차단한다. 로컬 파일 게시와 SMTP 호출 직전에 현재 동의와 임대를 다시 검사한다.

## 완료 게이트

원본 사이트 현재 동작과 실제 Ego 화면 조작, 선행 P06-T05 전체 게이트, 외부 SMTP/SMS 공급자·발송 정책 검증은 따로 필요하다. 로컬 사본 생성이나 합성 수신 검증을 외부 실제 발송 성공으로 기록하지 않는다. 검증 전에는 Task 상태를 완료로 바꾸지 않는다.
