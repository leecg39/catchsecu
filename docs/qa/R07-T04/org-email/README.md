# 조직 로그인 이메일 소유 확인 체크포인트

이메일 없는 가상 조직 구성원이 입력한 주소를 곧바로 verified로 처리하던 문제를 수정했다. PIN 인증은 조직 신원만 확인하며, 신규 이메일은 별도로 받은 6자리 인증번호를 검증한다. 외부 GPKI·새올·그룹웨어 기관 연동 성공을 의미하지 않는다.

- `OrgEmailChallenge`와 migration108 추가: ticket/회사/공급자/디렉터리 버전/이메일/코드 결합, 암호화 메일·해시, 5분 또는 티켓 만료 중 빠른 기한, 오답5회·재전송60초·구성원10회/시간.
- 잘못된 번호 횟수는 커밋한다. 정답은 디렉터리 등록·JIT 사용자·연결 계정·세션/MFA·감사와 같은 트랜잭션에서 티켓/challenge를 소비한다. 계정 충돌·감사 실패·최종 만료는 모두 롤백한다.
- 공급자 state가 있는 로그인·초대도 이메일 등록으로 전환하고 원래 초대/만료 정보를 보존한다. `/gpki/email-register` 전용 화면은 탭별 sessionStorage로 티켓·이메일·발급 정보를 복구하고 PIN/OTP는 저장하지 않는다. 저장소 차단 시 현재 화면에서 이어갈 수 있다.
- 메일 worker는 실제 발송 직전 회사·공급자·정책·디렉터리·티켓·번호·lease 상태를 다시 확인한다. 전역 worker는 실행하지 않았다.

[서버 회귀 결과](../../R07-T02/org-email/regression.json): 고유7파일274개 통과. 최초53개 중1개 실패는 worker 완료 상태를 succeeded로 잘못 기대한 테스트였고 실제 계약 done으로 수정했다. 확대272개 중1개 실패는 새 발급 경로 추가에 따른 정적 계약 작업 수18→19 미갱신이었다. 최신 조직인증37개·계약5개 재실행 통과 결과로 교체 집계했으며 이전 실패 보고서를 보존했다.

[실제 HTTP](http.json)16개, [재시작 검증](restart.json)1개 통과. 소유자 검증·회사 준비는 명시적 DB fixture이며, 대상 구성원은 실제 발송된 로컬 메일의 번호로 등록했다. SMTP 외부 전달은 미검증이다. 디렉터리v2·연결계정1·OTHER 인증근거1·소비 후 티켓/challenge0·감사12건. 상태해시 `2c89f4bbccf07f988ab4cc065c6aa85fdf0f49f11dd307a657787f7ab219d4f4`가 재시작 후 일치했다. 앞선 정책 writer의 상태해시도 보존됐다.

[독립 검토](read-only-review.json)에서 만료 티켓의 발급한도 소모를 찾아 수정하고 회귀를 통과했다. [브라우저 검증](browser-pending.json)은 Ego 복구 공간 생성 답변 대기다. 화면 구현만으로 화면 수용을 완료로 올리지 않는다.

필수 후속은 SSO callback의 시작 브라우저 결합(login CSRF 방어), 운영 SSO outbound DNS/사설IP 차단, 실제 HTTPS IdP 시험, 공급자 편집의 회사 문맥/입력보호, 원본 인증18경로·정책2경로의 화면 수용이다. 이들은 승인된 전체 작업 범위에 포함되며 다음 단계에서 계속한다. 전체107작업은51진행/56계획/0완료, goal active를 유지한다.
