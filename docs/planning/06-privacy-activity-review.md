# 개인정보 활동 검토 이력 독립 구현 명세

2026-10-04. 모델/API/UI 부분 구현 단계이며 전체 완료 증거가 아니다. 사용자 요청은 미완료 기능 구현까지이며, 원본의 빈 화면을 그대로 완료로 인정하지 않는다.

## 확인한 원본과 현재 결손

`docs/research/management/my-page--info-activity-log.json`은 수신일시·발신자·내용·구분·대상자·상태·메시지 발송 열과 빈 목록, ‘잘못된 접근입니다.’ 메시지만 보여준다. 정상 요청/답변 동작은 관찰되지 않았다. 착수 당시 `src/components/management/logs.tsx`는 고정 빈 배열이었다. 현재 이 경로는 `ActivityReviews.tsx`로 연결했다. `03-route-matrix.md`는 이 경로를 P12-T01에 매핑한다. 프로필 진입점은 P03-T03에 있으므로 두 Task에서 추적한다. 아래는 원본과 동일하다고 주장하지 않는 독립 업무 흐름이다.

## 사용자 흐름

1. 개인정보 처리로그에서 현재 서비스의 감사 기록을 선택한다. 보안 관리 권한이 있는 사용자는 해당 기록의 처리자에게 검토 요청과 설명을 보낸다. 자유 입력한 다른 회사/사용자에게 보내지 않는다.
2. 처리자는 마이페이지의 ‘개인정보 활동 검토 이력’에서 본인에게 온 요청을 읽고 설명을 답변한다. 자신의 기록에 대한 요청만 조회/답변할 수 있다.
3. 요청자는 보낸 요청과 답변을 확인하고 처리 완료 또는 요청 취소를 기록한다. 보안 담당자가 바뀐 경우 현재 해당 서비스의 보안 관리자가 처리할 수 있도록 권한을 다시 검사한다.
4. 목록은 받은 요청/보낸 요청 구분, 상태/날짜/검색, 서버 페이지, 최신 정보 재조회, 상세/답변/처리 내역을 제공한다. 동시 편집409에서 저장을 막고 최신 version을 불러온다.
5. ‘메시지 발송’은 실제 앱 내 요청/답변 이력으로 표시한다. 이메일 알림은 별도의 명시적 요청 동작과 Job 상태를 표시하며 외부 SMTP 성공은 공급자 검증 전 완료로 표시하지 않는다. 요청 생성과 외부 발송은 구분한다.

## 데이터와 권한

- ActivityReview: tenantId/serviceId/auditEventId/requesterMembershipId/recipientMembershipId, 요청 제목과 암호화한 본문, 상태, version, 생성/갱신/답변/종결 시각. 원본 감사 원장은 수정하지 않는다.
- ActivityReviewMessage: 동일 회사/검토 요청에 속한 작성자·본문 암호문·종류·시각. 메시지는 추가만 가능하며 답변 및 종결과 같은 transaction으로 기록한다.
- 회사/서비스/구성원은 composite FK로 교차 회사 참조를 금지한다. 감사 대상의 actor가 없거나 회사 구성원이 아니면 요청할 수 없다. 개인정보 처리(응답/파일/파기/업로드) 감사 종류에 한정한다.
- 요청 생성/회사 검토는 현재 security.write와 audit.read, 해당 서비스 범위를 검사한다. 조회/답변은 현재 회사 회원으로 자신의 수신 요청만 허용한다. 일반 감사 열람 권한만으로 검토 변경을 허용하지 않는다.
- 현재 회사, 계정, 세션, 이메일 인증, MFA/IP/비밀번호 정책, 전문가 배정, 최종 유효기한을 요청마다 검사한다. 구성원/서비스 회수와 상태 변경 중에도 원자성을 유지한다.
- 같은 감사 기록의 열린 요청은 중복 생성하지 않는다. 생성/메시지 재시도는 Idempotency-Key, 변경은 version을 요구한다. 재전송도 현재 권한/보유 상태를 재검사하고 민감 내용의 캐시 재노출을 막는다.
- requested → responded → resolved, requested/responded → cancelled. 종결 뒤 추가 답변/중복 종결은409. 본인 요청/답변의 경계와 마지막 권한 회수는 테스트한다.
- 감사에는 값이 아닌 변경 필드와 자원 ID만 남긴다. 목록에는 본문 전체/원문 개인정보/토큰/IP를 싣지 않는다. 상세는 허용된 사용자에게만 암호문을 복호화한다.

## 구현 순서와 검증

1. 별도 계약과 schema/migration: FK·unique·조회 인덱스·허용 상태/본문 길이/시각 제약. 빈 설치와 기존74 migration 이후 업그레이드·실패 복구를 확인한다.
2. 실제 PostgreSQL 서비스/API: 요청→답변→처리, 타 회사/서비스/타인/다른 역할, 세션·정책·배정 회수, 같은 키/다른 본문, 동시 version, 감사/메시지/Job 롤백을 시험한다.
3. 처리로그의 요청 버튼과 마이페이지 이력 화면 연결. 원래 열 의미를 보존하되 실제 사용자가 이해하는 상태/오류/빈 화면/권한 안내를 제공한다.
4. 두 합성 사용자로 실제 Ego 요청/답변/종결·검색/서버페이지·409·390px를 조작하고 독립 DB와 대조한다. 재로그인/같은 빌드 재시작 후 이력과 감사 해시를 확인한다.
5. OpenAPI/Task 매핑/구현 현황·QA를 갱신한다. 전체 관련 회귀·TypeScript·lint·production build를 통과한다. 외부 발송과 원본 정상 동작은 별도 증거 없이 완료로 올리지 않는다.
