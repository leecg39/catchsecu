# 실제 작동 검증과 완료 기준

## 증거 수준을 나눠 기록

| 단계 | 통과의 의미 | 통과로 보지 않는 것 |
|---|---|---|
| source_observed | 원본 특정상태 화면/네트워크 직접 관찰 | AST 존재, 403 빈화면, redirect |
| code_present | 모델·핸들러·화면 코드 존재 | 파일명만 있음, 범용 fallback |
| local_backend_verified | 실제 시험 PostgreSQL·HTTP·권한·트랜잭션 통과 | mock DB, 200 응답만 확인 |
| local_browser_verified | 브라우저 행동→API→DB→다른화면 반영 | 스크린샷 한장·성공toast만 |
| restart_verified | 서버/worker재시작·새 로그인 이후 일치 | 같은 React state나 localStorage 재조회 |
| external_verified | 실제 제공사/기관 시험환경 수신·receipt·실패/중복 대응 | mock adapter, 요청 accepted만 |
| source_fidelity_verified | 접근 가능한 원본 정상상태와 시각/행동 대조 | 미관찰 유료화면 임의추정 |

각 Task 증거에 코드 commit/작업트리 fingerprint·시각·환경·명령·fixture ID·HTTP status/body·독립 DB before/after·브라우저 캡처·외부 식별자를 기록한다. 민감 데이터/secret/token은 마스킹한다.

## 리소스별 CRUD 최소 시나리오

- C: 브라우저 입력→서버 검증→실제 DB row/관계/감사/outbox 확인→목록·상세·다른 화면 조회. 잘못된 입력·중복 submit·동일 idempotency-key/different payload·A/B회사 참조 주입을 시험한다.
- R: 빈/보유 데이터, 상세404, 기간·서비스·검색·정렬·페이지크기, 같은 시각 레코드의 페이지 안정성, 역할별 필드마스킹, 동일 필터 export를 검증한다.
- U: version 포함 변경→DB version 증가→목록/상세/집계 갱신. 2탭 동시수정409, 권한회수/보관/파기와 경합, 게시본 불변을 검증한다.
- D: 삭제/보관/해제/취소의 의미를 명세대로 확인한다. 참조중 삭제 충돌·2회삭제·권한없는삭제·보관후재조회/복구·실제파일 정리까지 확인한다.
- 상태 전이: 게시·승인·발송·환불·철회·파기는 허용표에 따라 시험한다. 성공 결과 URL 방문으로 원장/동의/인증을 생성하지 않는다.
- 읽기전용 리소스: 로그·원장·통계의 U/D는 서버에서도 불가해야 한다. 실제 원천업무를 수행해 생성과 집계 변경을 확인한다.

## 화면별 필수 상태

각 RR행은 정상·빈 상태·로딩·검증오류·네트워크실패·권한없음·기능권한없음·인증만료·충돌을 적용 여부와 함께 기록한다. 비해당은 이유를 쓰며 무조건 성공으로 채우지 않는다.

목록 CRUD는 생성모달/편집/삭제확인/검색초기화/선택행/페이지 이동을, wizard는 직접진입·뒤로가기·재로드·미저장 이동·단계간 객체 ID 유지·중복 저장을 확인한다. 모바일/키보드 focus·label·실패 메시지도 포함한다. 동적 경로는 존재/없음/타회사/만료 ID를 모두 만든다. wildcard2는 잘못된 경로와 보안 경계 검사로 다룬다.

## 작업별 완료 게이트

1. 모델/계약 변경이 없으면 “기존 계약 재사용” 근거를 남긴다. 변경 시 새 migration과 DTO/OpenAPI/정책표를 함께 갱신한다.
2. 해당 의미 있는 단위·DB 통합 테스트, typecheck, lint 및 build를 통과한다. 문구만 수정하는 작업에 구현을 복사한 테스트를 억지로 만들지 않는다.
3. 화면 action을 실제 수행하고 독립 DB조회·새로고침·재로그인·서버/worker재시작 증거를 수집한다. DB 수정과 브라우저 행동의 동일 resource ID를 기록한다.
4. 외부 의존성이 없으면 해당 Task를 완료할 수 있다. 외부 의존성이 있는 Task는 `local_verified_external_pending` 중간상태로 후속 내부작업에 계약을 제공할 수 있으나 전체 기능 완료로 세지 않는다.
5. 모든 증거를 `catchsecu-clone/docs/qa/Rxx-Tyy/`에 저장한다. README에 재현명령과 실패/수정/재실행 결과를 기재하고 root TASKS/tasks.json/goals를 동기화한다.

의존성 표의 다른 도메인 T04는 **로컬 수용 게이트 통과**를 후속 내부 구현 착수 기준으로 삼는다. 외부검증은 R25-T03이 끝날 때까지 추적하며 R25-T06 전체완료는 실제 외부검증을 요구한다. 자격증명이 없는 SMS 때문에 이메일 DB/UI 구현까지 멈추지 않는다.

## 통합 시나리오

1. owner가 회사·서비스·역할을 생성하고 편집자를 초대한다.
2. 편집자가 목적·제공자를 만들고 동의서/방침을 게시한다. 폼에 문서를 묶고 질문·첨부·보유기간을 저장한다.
3. 승인자가 승인하고 게시한다. 외부 브라우저가 필수동의·본인인증·첨부와 함께 제출한다. 원문·영수증·파일hash를 확인한다.
4. 개인정보 담당자가 조회·정정·메모·내보내기·제한된 외부공유를 실행한다. 정보주체는 자기 동의만 조회한다.
5. 광고동의 대상만 문자/메일/알림톡을 예약하고 알림이 전송된다. 직전 철회·권한회수·잔액부족·provider실패를 각각 주입한다.
6. 사용량 원장·청구/환불·이메일억제와 발송receipt를 대조한다. 중복/역순callback에도 원장이 한 번만 변한다.
7. 파기를 보류·해제·승인해 실제 DB/파일/파생내보내기 접근이 사라지는지 확인한다. 로그·증명서·월마감·통계의 최소근거는 일치해야 한다.
8. 서버/worker를 재시작하고 다른 브라우저로 재로그인한다. 모든 상태를 다시 조회하고 A/B회사 격리를 반복한다.

## 계획 검산과 기능검증 명령 구분

이번에 실행하는 명령은 이 폴더의 `python3 verify_plan.py`뿐이며 문서의 경로·모델·API·의존성·기존파일보존을 검사한다.

구현 단계는 저장소의 현재 scripts를 읽고 환경 가드를 확인한 후 관련 `npm run typecheck`, `npm run lint`, `npm run build`, 선별 `npm test`, DB/API/fixture 검증 및 브라우저 QA를 실행한다. 기존 `npm run verify:plan`은 181 hardcode가 있으므로 R00에서 고친 다음 사용한다. 기존 테스트가 있다는 이유로 모두 통과했다고 보고하지 않는다.
